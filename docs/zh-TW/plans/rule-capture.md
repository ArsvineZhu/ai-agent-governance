# Rule Capture（TASK 計劃）

[English](../../en/plans/rule-capture.md) · [简体中文](../../zh-CN/plans/rule-capture.md) · [繁體中文](rule-capture.md)

> **狀態：設計計劃，未實作。** 交付對帳（`scripts/check-plan-delivery.js`）跳過純設計計劃；本行即標記。

### 任務目的

不讓治理要求只活在對話上下文裡。開發者在任務過程中提出的每條**持久性**要求，必須在任務宣稱完成前落進規則檔案（`AGENTS.md` / `docs/rules/**`）——這樣換開發者、換電腦、換會話時，新 Agent 繼承的是同一套約束，而不是又開始「想當然」地亂改。

### 當前問題

對話裡提的要求當場生效（Agent 本輪會遵守），但從不寫進治理體系。上下文一結束就蒸發：

- 本次會話產生 5 條明確要求：只有 3 條完整落地，1 條只寫進了被治理專案範本、**本倉庫自己的 AGENTS.md 沒寫**，還有 1 條（「優先完善現有機制而非新增」）**任何檔案裡都沒有**。
- 六階段生命週期同步的是 程式碼 → 文件（CHANGELOG / Feature Registry / 架構），**沒有任何一條義務涵蓋「口頭要求 → 規則檔案」**。
- 結果：治理看起來實作了（Agent 整場表現正確），但倉庫裡根本沒有——下一個 Agent 一無所知。

第二個更隱蔽的問題：Agent 無法可靠區分**持久規則**與**一次性指令**。全自動寫入會用一次性決定汙染規則庫（例如「這次單次提交」只綁定那一堆混合改動）；反過來讓開發者自己列「哪些該留」，等於把梳理工作推回去，還容易被一句「隨便吧」敷衍掉。

### 提議方案

**AI 預分類、開發者裁定、一次任務一輪確認、未確認者留痕。**

1. **任務中收集** —— Agent 記錄開發者提出的每一條要求。
2. **Phase 6 預分類** —— 報告給出規則沉澱清單，每條帶**結論**而不是提問：
   - `[持久]` + 建議寫入的檔案/章節
   - `[一次性]` + 為何綁定本次任務
   - `[模糊]` + 明確請開發者裁定
3. **開發者裁定** —— 一句話確認或改判。
4. **寫入** —— 確認為持久的規則走治理檔案保護流程寫入 `AGENTS.md` / `docs/rules/**`（原因 → CHANGELOG → 跑校驗器；受保護檔案完整清單見 `references/policies/governance-files.policy.md`，單一事實來源，本頁不複述）。寫入絕不靜默、絕不免確認：規則檔案是受保護工件，Agent 無監督地給自己寫約束，正是「Agent 不得自我解除限制」要禁止的反面。
5. **留痕** —— 未確認/未裁定的候選寫入 `.governance/activity.jsonl` 的 `rules_pending` 欄位，保證不靜默消失，drift-check 能報「有 N 條候選規則未沉澱」。

**分類判據（寫入規則正文）：**

| 訊號 | 判為 |
| --- | --- |
| 祈使句 + 通用行為（「以後都」「任何時候」「不要再」）；約束行為模式；已重複出現 | 持久規則 |
| 綁定具體物件（「這個檔案」「這次」）；含範圍限定詞（「先」「暫時」「就這一次」）；執行完即失效 | 一次性指令 |
| 判斷不了 | 模糊 —— 開發者裁定 |

**為何不做全自動**：規則檔案受治理保護；涉及權限/安全/校驗的改動必須使用者明確確認。而且代價不對稱——漏記一條規則的成本是重說一句話，錯記一條是**永久的錯誤約束**，事後沒人會回頭稽核。

### 受影響檔案

- `references/policies/lifecycle.policy.md` —— Phase 5 增加**規則捕獲**同步項；Phase 6 報告增加**規則沉澱清單**小節
- `references/templates/agents-md.template.md` —— Phase 5 摘要加規則捕獲；Documentation Map 分類補「開發者新提的普適要求 → `docs/rules/**`」
- `references/templates/sub-skills.md` —— state-manager 寫入 `rules_captured` / `rules_pending` 到 `.governance/activity.jsonl`；drift-check `activity-report` 模式暴露待沉澱候選
- `AGENTS.md` —— 本倉庫自身的同等義務（並補齊本次會話漏掉的兩條規則）
- `CHANGELOG.md` —— Added 條目

### 風險

- **報告膨脹** —— 每個任務末尾都掛規則清單，對小改動是雜訊；緩解：小型任務僅在存在候選時列出，否則一行「無新規則」
- **誤分類** —— Agent 把一次性判成持久；緩解：寫入前必經開發者裁定，且判據表把模糊情況偏向 `模糊` 而非 `持久`
- **受保護檔案摩擦** —— 每條捕獲規則都觸發治理檔案保護流程（CHANGELOG + 校驗器）；緩解：同一任務的所有捕獲規則合併為一次受保護檔案改動
- **候選堆積** —— 開發者一直拖延會讓 `rules_pending` 無限增長；緩解：drift-check 報告數量，把債務顯性化

### 驗證方法

- 構造含一條持久 + 一條一次性要求的任務 → Phase 6 報告兩條判定正確（狗糧驗證，人工）
- 確認後的規則出現在目標規則檔案 + CHANGELOG 有條目（文件斷言）
- 未確認的候選出現在 `.governance/activity.jsonl` 的 `rules_pending`（測試）
- drift-check `activity-report` 模式報出待沉澱候選數（測試）
- 本次會話漏掉的兩條規則回填進本倉庫 AGENTS.md（文件斷言）
